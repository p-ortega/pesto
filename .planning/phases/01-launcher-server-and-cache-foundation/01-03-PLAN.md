<objective>
Pointing pesto at a run directory now produces a real answer to "where does this run's cache live?" —
`.pesto/` inside the run when that directory will accept a write, a stable path under
`~/.cache/pesto/` when it will not, and an explicit override ahead of both. The layout underneath it
is the on-disk shape every later phase's ingest code writes into.

This is the phase's second capability, and it expands outward from the tracer rather than layering
under it: after this plan `pesto <run_dir>` does something a user can see that it could not do
before — it creates that run's cache and tells them where it went.

Purpose: settle the durable interface first. CONTEXT.md's Integration Points name
`pesto.cache.layout` as the lasting output of this phase — Phases 2, 3 and 4 all write through it,
while the launcher is only scaffolding by comparison.
Output: `resolve_cache_root`, `CacheLayout`, `for_run` and `ensure_gitignored`, wired into the CLI.
</objective>

    `_fallback_root(run_dir)` returns
    `Path(os.environ.get("XDG_CACHE_HOME", Path.home() / ".cache")) / "pesto" / digest`, where
    `digest` is the first 16 hex characters of `hashlib.sha256(str(run_dir.resolve()).encode())`.
    Keying on `.resolve()` is what makes equivalent spellings of one directory — trailing slash, a
    `.` segment, a symlink — land on one cache instead of three, and what keeps two genuinely
    different directories apart. Honouring `XDG_CACHE_HOME` when set is what lets the tests redirect
    the fallback without touching the developer's real home.

    `resolve_cache_root(run_dir, override=None)`:
    - If `override` is not None, return `Path(override)` immediately. An override is taken as given —
      never probed, never fallen back from. This is the outermost of three precedence levels and the
      order is total: override, then the run directory, then the user cache.
    - Otherwise require that `Path(run_dir).is_dir()`. If it is not, raise `NotADirectoryError`
      naming the path. This is the deliberate answer to the missing-input case: creating the run
      directory would let a mistyped path look like a successful open, and quietly filing a cache for
      a directory that does not exist would hide the same mistake in a place the user never looks.
      A missing run directory is a caller error, not a writability failure, so it must not be folded
      into D-04's fallback.
    - Then attempt the probe: `candidate.mkdir(parents=True, exist_ok=True)`, write a zero-byte file
      at `candidate / f".probe-{uuid.uuid4().hex}"`, and unlink it. Wrap the whole attempt in
      `try/except OSError` and return `_fallback_root(Path(run_dir))` from the except branch. Do not
      narrow the exception list and do not enumerate the failure modes in code: D-04's entire point is
      that the interesting failures are the ones nobody predicted, including ones that only appear on
      somebody else's machine. Do not decide writability by looking at the directory's mode bits and
      do not call `statvfs` for free space; the probe is the decision. Name the probe file with a
      fresh uuid4 each call so two pesto processes probing the same directory at the same moment
      cannot unlink each other's file. Unlink it in the success path so nothing is left behind in a
      directory pesto does not own.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pesto → the user's run directory | pesto writes into a directory it does not own, holding irreplaceable calibration output. Everything it writes there must be bounded and reversible. |
| pesto → the user's git repository | The `.gitignore` append modifies a version-controlled file in the user's repository. |
| pesto → `~/.cache/pesto/` | The fallback root is derived from a path string; a bad derivation writes outside the intended tree. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-08 | Tampering | `ensure_gitignored` appending to the user's `.gitignore` | medium | mitigate | Append-only, one line, guarded by a read-check so repeated launches cannot accumulate duplicates; existing content is never rewritten or reordered, and the function returns without writing when no `.git` is present. Covered by the byte-for-byte preservation test. |
| T-01-09 | Tampering | probe-file write inside `<run_dir>/.pesto/` | low | mitigate | Zero-byte file, uuid4-named so concurrent processes cannot unlink each other's, unlinked on the success path, and confined to the `.pesto/` subdirectory rather than the run directory itself. |
| T-01-10 | Tampering | `_fallback_root` deriving a path under `~/.cache` from a run-directory string | medium | mitigate | The path component is a 16-character hex sha256 digest, not user text, so no run-directory name — however odd — can escape `~/.cache/pesto/` through traversal segments or separators. |
| T-01-11 | Denial of Service | a run directory on read-only or failing media | low | mitigate | The probe converts every write failure into the user-cache fallback rather than an exception, so unwritable media degrades instead of blocking (D-04). |
| T-01-12 | Tampering | symlink or junction inside the run directory redirecting the probe write or the `.gitignore` append | low | accept | Phase 1 is single-user and trusts its own filesystem; RESEARCH.md § Known Threat Patterns records this as out of scope here and worth revisiting in Phase 4/5 research if pesto is ever pointed at untrusted directories. Canon path-traversal handling is `/gsd-secure-phase`'s, not a bespoke prohibition. |
</threat_model>
