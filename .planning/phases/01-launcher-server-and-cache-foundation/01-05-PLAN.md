<objective>
Confirm by hand the two things in this phase that no test can assert.

Everything else in Phase 1 is covered by automation: the port binds, the token gate refuses, the cache
resolves, the manifest goes stale. Two claims are not automatable and both sit in the phase's stated
success criteria. First, that a browser window actually appears — `webbrowser.open` reports success
even when nothing happens, which is the entire reason D-10 requires the URL be printed regardless, so
only a person looking at a screen can close this. Second, that it appears *fast*, which is a
perceptual judgment about the phase's core value ("it has to feel instant") rather than a number.

This is the only human gate in the phase and it comes last, so it is one look at finished work rather
than a series of interruptions.

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 1: Confirm the browser opens, opens fast, and the printed URL works</name>
  <precondition>This is being run in a desktop session with a default browser available — not over a headless SSH connection. `webbrowser.open` cannot raise a GUI on a headless host, so the first two steps below would fail for a reason that has nothing to do with pesto. If the session is headless, say so rather than approving: step 3 (pasting the URL) is still meaningful and steps 1-2 should be deferred to a desktop session.</precondition>
  <what-built>
    Plans 01-02 through 01-04 are complete and their automated suites are green:

    - `uv run pesto` starts a server on a free `127.0.0.1` port, mints a per-launch session token,
      prints the URL, and opens a browser at it once the socket genuinely accepts connections.
    - Every request without a local `Host` header and a valid token is refused — `/api/health`
      included. There is no unauthenticated route.
    - `uv run pesto <run_dir>` resolves that run's cache to `<run_dir>/.pesto` when the directory
      accepts a write, or to a stable path under `~/.cache/pesto/` when it does not, prints which one
      it picked, and adds a single `.pesto/` line to the run's `.gitignore` when it is a git repository.
    - The cache manifest can say whether each artifact is stale, cheaply by size and mtime and then by
      whole-file checksum when those disagree.

    What automation cannot confirm: that a browser window appears at all, and that it appears fast
    enough to feel immediate. Launching a browser reports success even when nothing appears — pesto
    cannot detect its own failure here, which is why D-10 prints the URL unconditionally.
  </what-built>
  <how-to-verify>
    1. **A browser opens, with no arguments.** In a terminal, run `uv run pesto`. A browser window or
       tab should appear on its own. It will show a bare or "not found" page — there is no frontend
       until Phase 5, so an empty page is the expected and correct result here. What matters is that a
       window appeared without you doing anything, because that is the double-click story D-09 exists
       to protect. Press Ctrl-C to stop the server.

    2. **It feels immediate.** Run `uv run pesto` again and watch the gap between pressing Enter and
       the window appearing. It should read as "instant", the way opening a text editor does — not as
       a program loading. The budget is about 150 ms and the reason it is reachable is that nothing at
       import time touches pyemu or flopy; those load on a background thread after the port is bound.
       If instead there is a visible pause of a second or more before the window appears, that is the
       defect this step exists to catch — say so rather than approving. Ctrl-C to stop.

    3. **The printed URL is the real one.** Run `uv run pesto --no-browser`. Copy the
       `pesto serving http://127.0.0.1:<port>/?token=<token>` line from the terminal and paste it into
       a browser yourself. You should reach the same page as in step 1. Then delete the
       `?token=<token>` part from the address bar and reload: you should get a refusal, not the page.
       That pair is D-01 and D-10 working together — the URL is always printed so a remote session or
       an unusual desktop setup is never locked out, and the token is what actually grants access.
       Ctrl-C to stop.

    4. **A real run directory.** Copy one benchmark run somewhere writable first — the originals on
       `/Volumes/Gandalf/intera` are read-only and must stay untouched:
       `cp -R ~/dev/data/pesto-bench/forecast_20250618105403 /tmp/pesto-check-run`
       Then run `uv run pesto --no-browser /tmp/pesto-check-run`. Confirm it prints the cache root it
       chose, that the command returns to serving immediately rather than grinding through gigabytes
       (Phase 1 reads no PEST file, so an immediate return is the correct behaviour), and that
       `ls -a /tmp/pesto-check-run/.pesto` shows the `control ens reals agg grid phi time` directories.
       Ctrl-C to stop, then `rm -rf /tmp/pesto-check-run`.

    5. **A directory that will not take a write.** `mkdir /tmp/pesto-readonly && chmod 500 /tmp/pesto-readonly`,
       then `uv run pesto --no-browser /tmp/pesto-readonly`. It should print a cache root under
       `~/.cache/pesto/` instead of inside the directory, and start normally rather than erroring —
       that is D-04's fallback working on your actual filesystem, not in a mocked test. Ctrl-C, then
       `chmod 700 /tmp/pesto-readonly && rmdir /tmp/pesto-readonly`.
  </how-to-verify>
  <resume-signal>
    Type "approved" if all five steps behaved as described. Otherwise name the step number and what
    you saw — in particular, report a visible pause in step 2, a window that never appeared in step 1,
    or a cache landing somewhere you did not expect in steps 4 or 5.
  </resume-signal>
