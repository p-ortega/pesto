<objective>
The first end-to-end slice of pesto: a command that starts a server on a free loopback port, mints a
session token, prints the URL, opens a browser only once the socket genuinely accepts connections,
and refuses every request that does not carry both a local `Host` header and the token.

This is the phase's tracer. It is written for keeps — it is not a prototype and it carries no
throwaway scaffolding. The whole launch path is proven on one thin route (`/api/health`) so the
architecture is confirmed before Phases 2 through 5 pile roughly twenty more routes on top of it. The
token gate is deliberately inside the tracer rather than added later, because CONTEXT.md rates D-01's
undo cost as **costly**: retrofitting the check after Phase 5 means touching every route handler and
every test that calls one.

Purpose: prove the launcher, the loopback boundary and the request gate all work together, on the
agent's best early-context tokens, before any of it has consumers.
Output: an installable `pesto` package whose console script serves a gated `/api/health` on a random
loopback port.
</objective>

<resolved_open_questions>
RESEARCH.md left two open questions. Both are settled here so no acceptance criterion is ambiguous.

**Q1 — does `/api/health` require the session token? Yes. There is no carve-out.**
D-01 is a locked decision and reads universally: "The server rejects any request that does not carry
it." An exemption would be the planner narrowing a locked security decision, and the liveness-probe
argument that motivated RESEARCH.md's assumption A3 does not apply to pesto: there is no Kubernetes
probe, no container healthcheck and no external orchestrator. The only callers of `/api/health` are
pesto's own tests and, from Phase 5, its own frontend — both of which hold the token. So the M0
plan's tokenless `curl` verification step is the thing that changes, not D-01. Every acceptance
criterion below curls with the token, and asserts 401 without it.

**Q2 — is the browser-open race fix its own task? No, it folds into the launcher.**
It is a rewrite of one function (`serve`), not new scope. The researcher recommended folding it in;
this plan does. `serve()` constructs `uvicorn.Config` and `uvicorn.Server` directly instead of
calling `uvicorn.run()`, purely so `Server.started` is available as a real readiness signal.
</resolved_open_questions>

<assumption_delta_decision>
The deterministic detector fired `pluralization` on this phase's scope, from the design spec's
requirement that pesto be reachable "not from another machine, **not from another user on the same
machine**". A second case was introduced where there had been one, so the identity model is worth
re-asking rather than extending by habit.

- **The noun that is now primary: the session.** Access used to be identified by *network origin* —
  "did this arrive on loopback" was the whole answer. With a second threat origin admitted (a page or
  process belonging to a different user on this same machine), network origin can no longer be the
  primary identity, because it cannot distinguish two callers that share a loopback interface.
- **Decision: `promote`.** The per-launch session token becomes the primary access-control identity.
  Loopback binding and the `Host`-header check are demoted to defence-in-depth details that narrow
  *where* a caller may come from, not *who* it is. Concretely: the token check is not a second gate
  bolted beside the host check — it is the gate, and it applies to every route including
  `/api/health`.
- **Why not `add-alongside`:** keeping "reachable on loopback" as a co-equal primary is what produces
  the tokenless-health carve-out, and a carve-out is precisely a route that the primary identity
  cannot confirm. That asymmetry is the debt this decision avoids.
- **Invariant test accepted** (Task 2): iterate the app's own route table and assert every route
  refuses a tokenless request. It goes red the instant a later phase reintroduces the singular
  assumption by registering a route outside the gate.
</assumption_delta_decision>

    `mint_token()` returns `secrets.token_urlsafe(32)`; never `random`, never `uuid4`.
    `LOCAL_HOSTNAMES = {"127.0.0.1", "localhost", "::1", "[::1]"}`.
    `_hostname_only(host_header)` strips the port, keeping bracketed IPv6 literals intact
    (`"[::1]:53211"` yields `"[::1]"`, `"127.0.0.1:53211"` yields `"127.0.0.1"`).

    (1) refuses a non-local hostname with 400 and (2) refuses a token failing
    `hmac.compare_digest` with 401 — in that order, so a foreign host never learns whether its token
    was right. Both refusals return `application/problem+json` bodies naming the failure, matching the
    shape SERVE-02 will formalise in Phase 5. Use `hmac.compare_digest` for the comparison; a direct
    equality test leaks how many leading characters matched. Do not reach for Starlette's bundled
    host-allowlist middleware: RESEARCH.md § Alternatives Considered documents a port-handling defect
    (Kludex/starlette #1997/#1998) and pesto's port changes every launch, so a fixed allowlist is the
    wrong shape anyway.

    **`src/pesto/launch.py`** — follow PATTERNS.md Pattern 2.
    `find_free_port()` binds a `socket.socket()` to `("127.0.0.1", 0)` and returns
    `int(sock.getsockname()[1])`. `serve(host="127.0.0.1", port=None, open_browser=True,
    run_dir=None)` resolves the port, calls `create_app()`, stores
    `app.state.initial_run_dir = str(run_dir) if run_dir else None`, builds
    `url = f"http://{host}:{port}/?token={token}"`, constructs
    `uvicorn.Config(app, host=host, port=port, log_level="warning")` and `uvicorn.Server(config)`,
    then starts one daemon thread named `pesto-after-startup` which waits on `server.started` in a
    5 ms `time.sleep` loop before doing three things in order: starting a second daemon thread named
    `pesto-warmup` that imports `warm_up` **inside the function body** and calls it; printing
    `f"pesto serving {url}"`; and calling `webbrowser.open(url)` when `open_browser`. Finally call
    `server.run()`, which blocks. Two things matter and both are gated on `server.started`, never on
    a fixed wall-clock delay: the warm-up must not begin until the port is genuinely accepting
    connections (that ordering *is* LAUNCH-01), and the browser must not be sent to a socket that
    will refuse it. Print the URL unconditionally per D-10 — launching a browser reports success even
    when nothing appears, so pesto cannot detect its own failure and must not pretend to.
    `find_free_port()` has a microsecond-wide race between releasing the probe socket and uvicorn
    binding; record it in the docstring as an accepted, extremely low-probability failure mode for a
    single-user local app rather than engineering around it (RESEARCH.md Pitfall 5).
